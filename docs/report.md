## Цель работы

Проектирование модели управления версиями ПО, конфигурациями и
непрерывной поставкой: освоить Terraform для описания инфраструктуры как
кода, Ansible для управления конфигурациями серверов и поднять локальный

## Задание 1 - Terraform и Docker

Для первого задания выполнены все семь шагов учебного руководства
Terraform Get Started на Docker-провайдере `kreuzwerker/docker`.
Конфигурация лежит в `task1/` и покрывает каждый шаг:

1. Build Infrastructure - `terraform init`, `plan`, `apply` создали
   ресурсы `docker_image.nginx` и `docker_container.nginx`, контейнер
   `lab5-nginx` ответил на `http://localhost:8090` страницей nginx.
2. Change Infrastructure - изменил `external_port` с 8090 на 8095,
   `terraform apply` показал «1 to change» и пересоздал контейнер без
   ручного удаления, страница открылась уже на 8095.
3. Define Input Variables - имя образа, имя контейнера и порт вынесены в
   `variables.tf`, переопределяются флагом `-var`.
4. Output Data - в `outputs.tf` описаны `container_id`, `image_id` и
   `container_url`, читаются командой `terraform output`.
5. Query Data Sources - `data "docker_image" "nginx"` читает метаданные
   образа до создания ресурса, ресурс ссылается на него.
6. Destroy Infrastructure - `terraform destroy` удалил контейнер. Образ
   помечен `keep_locally = true`, потому что тот же тег `nginx:1.28-alpine`
   используется контейнером из первой лабораторной, и удалять его было
   нельзя.
7. Весь цикл прогнан локально, результаты проверены `docker ps` и
   `curl`.

## Задание 2 - Ansible

Управляемыми узлами выступили три ноды kind-кластера из задания 3. Так
как это Docker-контейнеры без SSH-сервера, подключение настроено через
connection-плагин `community.docker.docker` - Ansible заходит в контейнер
командой `docker exec` и выполняет стандартные модули (на нодах есть
Python 3.11, так что модули работают в полном объёме, а не только `raw`).

В `task2/inventory/hosts.ini` хосты сгруппированы в `control_plane`,
`workers` и общую `k8s_nodes`, переменные группы задают тип подключения.
Проверены ad-hoc команды:

```sh
ansible k8s_nodes -m ping                      # pong со всех трёх нод
ansible k8s_nodes -m shell -a 'hostname; uptime'
ansible workers -m command -a 'cat /etc/os-release | head -2'
ansible workers -m service -a 'name=nginx state=restarted'
```

Написаны два плейбука. `node-setup.yml` обновляет кеш apt на всех нодах,
ставит `curl`, `htop`, `jq` и раскладывает файл-метку с именем ноды.
`nginx-workers.yml` устанавливает nginx только на группу `workers`,
подменяет стартовую страницу, запускает и включает службу, а handler
перезапускает её после смены страницы; ответ проверяется HTTP-запросом.
Оба плейбука отработали без ошибок: `ok=6` на трёх нодах и `ok=7` на
двух worker-нодах соответственно.

## Задание 3 - кластер Kubernetes и деплой приложения

Кластер создан по варианту 2 методички - kind через Docker-in-Docker:
каждая виртуальная машина кластера - это контейнер. Инфраструктура
описана в Terraform провайдером `justenwalker/kind` (`task3/main.tf`):
одна control-plane нода с пробросом порта 30080 и две worker-ноды, образ
`kindest/node:v1.34.0`. `terraform apply` поднял кластер за ~30 секунд,
`kubectl get nodes` показал все три ноды в Ready.

Деплой выполняет Ansible-плейбук `task3/ansible/deploy-app.yml`. Сначала
он загружает пять локальных образов приложения из лабораторной 1 в ноды
командой `kind load docker-image`, затем через модуль
`kubernetes.core.k8s` применяет манифесты из `task3/manifests/`:
namespace, Secret, PostgreSQL с PVC, Redis, Job миграций Liquibase,
Deployment api в двух репликах и nginx с Service типа NodePort.
Реплики api разнесены на разные worker-ноды через podAntiAffinity.

Из практических нюансов: в Kubernetes `command` подменяет ENTRYPOINT
образа, поэтому для Job'а Liquibase аргументы вынесены в `args`, как и в
docker-compose; ожидание готовности базы сделано init-контейнером с
`pg_isready`.

Проверка конца в конец: `kubectl get pods -o wide` показал все поды
Running на двух worker-нодах, миграции завершились успешно
(«Update has been successful»), `curl http://localhost:30080/health`
вернул `{"status":"ok","environment":"kubernetes"}`, а POST на
`/api/v1/clients` создал клиента - значит, работает вся цепочка
nginx -> api -> PostgreSQL.

## Контрольные вопросы

**1. Для каких задач применяется Ansible?**

Ansible применяется для управления конфигурациями и автоматизации работы
с серверами: установка и настройка ПО, раскатка приложений, оркестрация
процедур на множестве машин, выполнение разовых команд на группе узлов.
Работает по push-модели без агентов на управляемых машинах - достаточно
SSH (или другого connection-плагина, как docker в этой работе).

**2. Какие способы управления серверами применяются в Ansible?**

Два основных способа. Первый - ad-hoc команды (`ansible <группа> -m
<модуль> -a "<аргументы>"`) для разовых действий. Второй - плейбуки
(`ansible-playbook`), где желаемое состояние и шаги описаны декларативно
в YAML и применяются идемпотентно. Подключение к узлам идёт через
connection-плагины: ssh по умолчанию, также winrm, docker, local и др.

**3. Что входит в состав файла Ansible playbook?**

Плейбук - это YAML-файл со списком play. В каждом play указываются hosts
(на какие группы применяется), переменные, gather_facts, become, и
основные разделы: tasks - список задач с модулями, handlers - задачи,
запускаемые по notify, а также опционально roles, pre_tasks/post_tasks.
Каждая задача вызывает модуль с параметрами (apt, copy, service, uri и
т.д.).

**4. Что такое группы узлов (хостов) в Ansible?**

Группа - именованный набор хостов в инвентарном файле, например
`[workers]`. На группу можно нацеливать команды и плейбуки, задавать
переменные через `[group:vars]`, строить иерархию через
`[parent:children]`. В работе группы `control_plane` и `workers`
позволили ставить nginx только на рабочие ноды, а `k8s_nodes` -
выполнять команды сразу на всех трёх.

**5. Как одной командой выполнить ping группы узлов (хостов)?**

`ansible <имя_группы> -m ping`, например `ansible k8s_nodes -m ping`.
Модуль ping проверяет не ICMP, а возможность подключения и работы Python
на узле, и возвращает `pong`.

**6. Что такое роль Ansible?**

Роль - стандартизированный способ упаковать связанные задачи, handler'ы,
переменные, файлы и шаблоны в переиспользуемую структуру каталогов
(`tasks/`, `handlers/`, `defaults/`, `vars/`, `files/`, `templates/`,
`meta/`). Роль подключается в плейбуке через `roles:` и позволяет
делиться наработками и не дублировать код.

**7. Что такое файл инвентаризации Ansible и как он используется?**

Инвентарь - файл (INI, YAML или динамический скрипт), в котором
перечислены управляемые хосты и их группировка по группам, а также
переменные подключения и групповые переменные. Ansible читает его при
каждом запуске (путь задаётся в `ansible.cfg` или флагом `-i`) и по нему
понимает, на какие узлы и с какими параметрами подключаться.

**8. Что такое специальная команда Ansible?**

Специальная (ad-hoc) команда - разовый вызов модуля на группе хостов без
написания плейбука: `ansible workers -m command -a "uptime"`. Удобна для
быстрых проверок и единичных действий; для повторяемых сценариев
используются плейбуки.

**9. Как перезапустить службу с помощью Ansible?**

Модулем `service` (или `systemd_service`) - ad-hoc:

```sh
ansible workers -m service -a "name=nginx state=restarted"
```

либо задачей в плейбуке: `service: name=nginx state=restarted`, чаще
всего через handler, вызываемый по `notify` из задачи, изменившей
конфигурацию службы.

**10. Что такое HashiCorp Terraform?**

Terraform - инструмент HashiCorp для описания и управления
инфраструктурой как кодом. Конфигурация пишется на декларативном языке
HCL, Terraform строит план изменений, сравнивает его с файлом состояния
и приводит реальную инфраструктуру к описанной через провайдеры
(облака, Docker, Kubernetes и сотни других).

**11. Что такое инфраструктура как код (IaC)?**

Подход, при котором инфраструктура описывается в файлах конфигурации,
а не настраивается вручную. Файлы хранятся в системе контроля версий,
изменения проходят ревью, окружения воспроизводимы и приводятся к одному
состоянию, а развёртывание автоматизировано и повторяемо.

**12. Как установить Terraform?**

Скачать бинарник с сайта releases.hashicorp.com (или установить через
пакетный менеджер - brew на macOS, apt/yum-репозиторий HashiCorp на
Linux), положить в каталог из PATH и проверить `terraform version`.
В работе использовался бинарник `~/bin/terraform` версии v1.13.4.

**13. Что такое провайдер в Terraform?**

Провайдер - плагин, через который Terraform умеет работать с конкретной
платформой: он объявляет набор ресурсов и data source'ов и переводит их
в вызовы API платформы. Провайдеры скачиваются `terraform init` из
реестра; в работе применялись `kreuzwerker/docker` (контейнеры и образы)
и `justenwalker/kind` (кластер kind).

**14. Объясните базовую структуру файла конфигурации Terraform.**

Файл `.tf` состоит из блоков. `terraform { required_providers { ...
} }` - требуемые провайдеры и версия. `provider "name" { ... }` -
настройка подключения провайдера. `resource "тип" "имя" { ... }` -
управляемый объект инфраструктуры. `data "тип" "имя" { ... }` - чтение
существующих данных. `variable "имя" { ... }` - входные параметры.
`output "имя" { ... }` - значения, выводимые после apply. Блоки
ссылаются друг на друга выражениями вида `docker_image.nginx.image_id`.

**15. Что такое файл состояния Terraform?**

`terraform.tfstate` - JSON-файл, в котором Terraform хранит отображение
ресурсов конфигурации на реально созданные объекты (их ID и атрибуты).
По нему Terraform понимает, что уже существует, и считает diff при
plan/apply/destroy. Локально файл хранится рядом с конфигурацией, в
командной работе выносится в remote backend. В git его не коммитят - там
могут быть чувствительные данные.

**16. Для чего нужна команда terraform destroy?**

`terraform destroy` удаляет все ресурсы, которыми управляет текущая
конфигурация, ориентируясь на файл состояния. Используется, чтобы
полностью убрать созданную инфраструктуру - например, снести тестовое
окружение. По сути это `apply` с планом «всё на удаление».

**17. Что такое состояние в Terraform?**

Состояние - сохранённое Terraform представление об управляемой
инфраструктуре: какие ресурсы созданы, их атрибуты и зависимости.
Конфигурация описывает желаемое, state фиксирует фактическое, и
Terraform сравнивает их при каждом плане. Без state Terraform не смог бы
понять, что именно он создал раньше.

**18. Как определить зависимости в Terraform?**

Явно - мета-аргументом `depends_on = [ресурс]` внутри блока. Неявно -
через ссылки: если ресурс использует атрибут другого
(`image = docker_image.nginx.image_id`), Terraform сам строит граф
зависимостей и создаёт объекты в правильном порядке. Порядок виден в
плане и в `terraform graph`.

## Вывод

В работе пройден полный цикл инфраструктуры как кода: контейнерная
инфраструктура описана и изменена через Terraform, ноды настроены через

трёхнодовый кластер Kubernetes поднят декларативно провайдером kind, а

репозитория командами `terraform apply` и `ansible-playbook`.
